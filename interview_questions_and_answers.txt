BLINKIT CLONE - INTERVIEW QUESTIONS & COMPREHENSIVE ANSWERS
===========================================================

SECTION 1: FRONTEND & REACT
---------------------------

Q1. Why did you choose Vite over Create React App (CRA)?
A: Vite is significantly faster because it uses native ES modules during development, eliminating the need to bundle the entire app before starting the dev server. It uses esbuild (written in Go) for pre-bundling dependencies, which is 10-100x faster than Webpack (used in CRA). This results in lightning-fast Hot Module Replacement (HMR) and a better developer experience.

Q2. How did you manage global state in this application? Why Context API instead of Redux?
A: I used the React Context API (e.g., `AuthContext`) for managing global state like user authentication status. Since the state requirements for this project were relatively straightforward and didn't involve complex, rapidly changing data across deeply nested components, Context API provided a lightweight, built-in solution without the boilerplate and overhead of a library like Redux.

Q3. Can you explain how you implemented client-side routing and protected routes?
A: I used `react-router-dom` to define page routes. To secure protected routes (like a user dashboard or checkout page), I created a wrapper component (e.g., `<ProtectedRoute>`). This component checks the global auth state. If a user is not authenticated, it uses the `<Navigate to="/login" />` component to redirect them. If they are authenticated, it renders the requested child component.

Q4. How did you integrate maps using Leaflet in React?
A: I used the `react-leaflet` library, which wraps Leaflet.js in React components. I utilized the `<MapContainer>`, `<TileLayer>` (to load map tiles from OpenStreetMap), and `<Marker>` components. To show live tracking, the marker's coordinates are passed via props, updating automatically as the state changes.

Q5. How do you handle performance optimization in your React application?
A: I implement lazy loading (`React.lazy` and `<Suspense>`) to split the code and load routes/components only when requested. I also optimize re-renders by using the `useMemo` and `useCallback` hooks to memoize expensive calculations or function references passed as props.

SECTION 2: BACKEND & NODE.JS / EXPRESS
--------------------------------------

Q6. Can you explain the flow of a request in your Express application?
A: A client sends an HTTP request which first hits the Express Router. The router passes the request through middleware (like CORS, body parsing, or JWT auth validation). The request then reaches the specific Controller function. The controller handles business logic, interacts with the database via Prisma ORM, formats the data, and sends a JSON response back to the client.

Q7. How does Inngest help in your application? Give an example.
A: Inngest handles asynchronous, long-running background jobs outside the main Node.js event loop. For example, when an order is placed, the server instantly returns a success response to the client. Meanwhile, an Inngest event is triggered to send an order confirmation email. Inngest handles this in the background, providing automatic retries if the email service temporarily fails.

Q8. Explain how you handled file uploads. Why use Multer and Cloudinary?
A: `multer` acts as middleware to process `multipart/form-data` requests and extract the image file. Instead of saving images locally (which isn't scalable for serverless deployments like Vercel), the image stream is uploaded directly to Cloudinary (a cloud storage provider). Cloudinary returns a secure URL for the image, which is then saved in our database.

Q9. How did you implement error handling across your Express API?
A: I utilized a centralized error-handling middleware. Controller logic is wrapped in `try-catch` blocks (or an async wrapper function). When an error is caught, it is passed to the `next(error)` function. This passes it to a global error handler middleware that standardizes the error message and HTTP status code before responding to the client, preventing the app from crashing.

SECTION 3: DATABASE & ORM (PRISMA & NEON)
-----------------------------------------

Q10. What is Prisma, and what advantages does it offer over writing raw SQL?
A: Prisma is a modern Object-Relational Mapper (ORM). Its primary advantage is type safety; database schemas are mapped directly to TypeScript types, meaning schema mismatches or typos are caught at compile-time rather than runtime. It also offers an intuitive query builder and handles automated database migrations, making development much faster and safer than writing raw SQL.

Q11. What is a Serverless Database (Neon), and why did you use it?
A: Neon is a serverless Postgres database. It separates storage and compute, allowing it to scale compute resources instantly based on traffic demand, and scale down to zero when idle. This makes it highly cost-effective and completely removes the operational overhead of provisioning and managing traditional database instances.

Q12. How are Users, Orders, and Products related in your schema?
A: 
- A `User` has a One-to-Many relationship with `Order` (one user can place many orders).
- An `Order` has a One-to-Many relationship with `OrderItem`.
- An `OrderItem` has a Many-to-One relationship with a `Product` (an order item represents a specific quantity of a specific product).

SECTION 4: AUTHENTICATION & SECURITY
------------------------------------

Q13. Explain how JWT authentication works in your project.
A: Upon successful login, the server generates a JSON Web Token (JWT) signed with a secret key, containing the user's ID in the payload. This token is sent to the client (often stored in localStorage or an HttpOnly cookie). For subsequent protected requests, the client sends this token in the HTTP `Authorization` header. The server verifies the token's signature to authenticate the user before granting access.

Q14. How did you secure user passwords? What is the role of salt?
A: I used the `bcrypt` library to hash passwords before saving them. Hashing is a one-way mathematical function. A 'salt' (a random string) is added to the password before hashing. This ensures that even if two users have the exact same password, their resulting hashes are completely different, protecting the database against pre-computed rainbow table attacks.

Q15. How do you handle CORS and why is it necessary?
A: CORS (Cross-Origin Resource Sharing) is a browser security mechanism that restricts web pages from making requests to a different domain/port than the one that served the web page. Since the frontend runs on `localhost:5173` and the backend on `localhost:3000`, I configured the `cors` middleware in Express to add specific HTTP headers that explicitly permit the frontend to communicate with the backend API.

SECTION 5: PAYMENTS & INTEGRATIONS
----------------------------------

Q16. How did you integrate Stripe for payments?
A: I implemented Stripe Checkout. When a user proceeds to pay, the frontend calls the backend. The backend uses the Stripe Node.js SDK to create a Checkout Session, passing in the cart items and amounts. It returns a Session URL to the frontend, which redirects the user to a secure Stripe-hosted payment page.

Q17. Did you implement Stripe Webhooks? Why are they crucial?
A: Yes. Webhooks are essential because relying on the frontend to tell the backend a payment was successful is insecure (the user might close the browser tab too early, or a malicious user could fake a success request). With Webhooks, Stripe sends a secure, server-to-server POST request directly to my backend (`checkout.session.completed` event) to confirm the payment, ensuring order status is updated reliably.

SECTION 6: SYSTEM DESIGN & ARCHITECTURE
---------------------------------------

Q18. How would you scale this application if the user base grew 100x?
A: 
- **Frontend**: Deploy static assets to a global CDN (Content Delivery Network).
- **Backend**: Run multiple Node.js instances behind a Load Balancer (horizontal scaling).
- **Database**: Add Read Replicas to offload read-heavy operations (like browsing the product catalog).
- **Caching**: Implement a Redis cache layer for frequently accessed data, dramatically reducing database queries.

Q19. How would you handle inventory management to prevent overselling?
A: I would implement database transactions with Row-Level Locking (e.g., using `SELECT ... FOR UPDATE` in Postgres). When a user attempts to check out, the database locks the specific product row. If two users try to buy the last item at the exact same millisecond, the database forces one transaction to wait, ensuring inventory never drops below zero.

Q20. Why might you use WebSockets instead of standard HTTP for Live Order Tracking?
A: Standard HTTP is unidirectional (client requests, server responds). For live delivery tracking, the server needs to push continuous GPS updates to the client. WebSockets create a persistent, bidirectional connection, allowing the server to stream real-time location updates to the client with very low latency, which is much more efficient than having the client repeatedly poll the server via HTTP.
