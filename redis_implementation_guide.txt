BLINKIT REDIS IMPLEMENTATION GUIDE
===================================

Purpose
-------
Redis should be added to the SERVER layer. The React client continues calling the
same Express API endpoints. Redis is not a replacement for Prisma; use Prisma as
the permanent database and Redis for short-lived data, caching, rate limiting,
and fast live delivery updates.

Recommended first features for this project
--------------------------------------------
1. OTP storage for registration
   Current location: server/controllers/authController.ts
   Current problem: otpStore is an in-memory Map. It is lost when the server
   restarts and is not shared between multiple server instances.
   Redis improvement: store each OTP with a 10-minute expiration.

2. Product and flash-deal caching
   Current locations:
   - server/controllers/productController.ts
   - server/routes/productRoutes.ts
   Client consumers:
   - client/src/pages/Products.tsx
   - client/src/pages/FlashDeals.tsx
   - client/src/pages/ProductPage.tsx
   - client/src/components/Home/PopularProduct.tsx
   Redis improvement: cache read-heavy product responses for 30-60 seconds.
   Clear related keys whenever an admin creates, edits, or deletes a product.

3. Live delivery location
   Current locations:
   - server/controllers/deliveryPartner.ts, updateLocation
   - server/controllers/orderController.ts, getOrderLocation
   - client/src/components/delivery/DeliveryDashboard.tsx
   - client/src/pages/delivery/DeliveryDashboard.tsx
   - client/src/pages/OrderTracking.tsx
   Redis improvement: store the latest location with a short TTL, for example
   60 seconds. This avoids writing GPS coordinates to Prisma every few seconds.

4. OTP and login rate limiting
   Add this after the basic features work. Limit repeated requests to
   /api/auth/send-otp and failed login attempts by IP/email using Redis counters.

What should NOT be stored only in Redis
---------------------------------------
Orders, users, products, payments, addresses, and order history must remain in
Prisma. Redis data can disappear. Use Redis only as a temporary copy or fast
lookup. Stripe webhook processing and final order updates must continue using
Prisma.

Step 1: Install the Redis package
----------------------------------
From the server directory:

    npm install redis

The official redis package works well with the current TypeScript Express server.

Step 2: Add environment variables
----------------------------------
Add these to server/.env. Do not commit server/.env.

    REDIS_URL=redis://localhost:6379

For Redis Cloud, use the secure connection string supplied by Redis Cloud, for
example:

    REDIS_URL=rediss://default:YOUR_PASSWORD@YOUR_HOST:YOUR_PORT

A local Redis installation is useful for development. Docker alternative:

    docker run --name blinkit-redis -p 6379:6379 -d redis:7-alpine

Step 3: Create the Redis connection
------------------------------------
Create this new file:

    server/config/redis.ts

Suggested content:

    import { createClient } from "redis";

    export const redis = createClient({
        url: process.env.REDIS_URL,
    });

    redis.on("error", (error) => {
        console.error("Redis error:", error);
    });

    export const connectRedis = async () => {
        if (!redis.isOpen) {
            await redis.connect();
            console.log("Redis connected");
        }
    };

Step 4: Connect Redis when the server starts
--------------------------------------------
Edit server/server.ts. Import connectRedis and make startup asynchronous:

    import { connectRedis } from "./config/redis.js";

    const startServer = async () => {
        await connectRedis();
        app.listen(port, () => {
            console.log(`Server is running at http://localhost:${port}`);
        });
    };

    startServer().catch((error) => {
        console.error("Failed to start server:", error);
        process.exit(1);
    });

Remove the old direct app.listen block so the server does not listen twice.

Feature A: Move registration OTPs to Redis
-------------------------------------------
File to change:

    server/controllers/authController.ts

1. Remove the OtpRecord interface and otpStore Map.
2. Add:

    import { redis } from "../config/redis.js";

3. In sendOtp, after generating the OTP, replace otpStore.set(...) with:

    await redis.set(`otp:register:${email.toLowerCase()}`, otp, {
        EX: 10 * 60,
    });

4. In register, replace the Map lookup with:

    const emailKey = `otp:register:${email.toLowerCase()}`;
    const savedOtp = await redis.get(emailKey);

    if (!savedOtp) {
        return res.status(400).json({
            message: "Verification code has expired or was not requested. Please request a new code."
        });
    }

    if (savedOtp !== otp.trim()) {
        return res.status(400).json({
            message: "Invalid verification code. Please check your email and try again."
        });
    }

5. After successful verification, replace otpStore.delete(...) with:

    await redis.del(emailKey);

The client does not need a change. `client/src/context/AuthContext.tsx` and
`client/src/pages/Login.tsx` can keep using /auth/send-otp and registration.

Feature B: Cache products and flash deals
------------------------------------------
File to change:

    server/controllers/productController.ts

Use stable keys such as:

    products:all
    products:category:<category>
    products:search:<search>:<filters>
    product:<id>
    products:flash-deals

For a simple first version, cache only flash deals and individual products.
Example for getFlashDeals:

    import { redis } from "../config/redis.js";

    const cacheKey = "products:flash-deals";
    const cached = await redis.get(cacheKey);

    if (cached) {
        return res.status(200).json(JSON.parse(cached));
    }

    const products = await prisma.product.findMany({
        where: { stock: { gt: 0 } },
        orderBy: { originalPrice: "desc" },
    });

    const productsWithDiscount = products.map((product: any) => {
        const discount = product.originalPrice && product.price
            ? Math.round(((product.originalPrice - product.price) / product.originalPrice) * 100)
            : 0;
        return { ...product, discount };
    });

    const response = {
        message: "Flash deals fetched successfully",
        products: productsWithDiscount.slice(0, 8),
    };

    await redis.set(cacheKey, JSON.stringify(response), { EX: 60 });
    return res.status(200).json(response);

For getProduct, use key product:<id> and an expiration of 300 seconds. Always
keep the existing Prisma lookup as the cache-miss path.

Cache invalidation is required. In these functions in
server/controllers/productController.ts:

    createProduct
    updateProduct
    deleteProduct

After the Prisma write, clear affected keys:

    await redis.del("products:flash-deals");
    await redis.del("products:all");
    await redis.del(`product:${req.params.id}`); // update/delete only

If many filtered product keys are added later, use Redis key scanning or a short
TTL rather than trying to manually track every possible query string.

Feature C: Cache live delivery location
----------------------------------------
Files to change:

    server/controllers/deliveryPartner.ts
    server/controllers/orderController.ts

Current frontend behavior:
- DeliveryDashboard sends lat/lng to PUT /delivery/my-deliveries/:id/location.
- OrderTracking requests GET /orders/:id/location every 10 seconds.

Important current issue: updateLocation currently reads req.body.orderId, but the
frontend puts the order ID in req.params.id. Change the handler to use:

    const orderId = req.params.id as string;

In updateLocation, validate the order with Prisma as it does today, then write
the latest location to Redis instead of updating Prisma on every GPS update:

    await redis.set(
        `delivery:location:${orderId}`,
        JSON.stringify({ lat, lng, updatedAt: new Date().toISOString() }),
        { EX: 60 }
    );

Keep the active-order authorization query before this Redis write. Do not allow a
partner to write a location for an order that is not assigned to that partner.
Also validate that lat and lng are numbers and are within valid coordinate ranges.

In getOrderLocation in server/controllers/orderController.ts, first read Redis:

    const cachedLocation = await redis.get(`delivery:location:${req.params.id}`);

If cachedLocation exists, return it with the current order status. Otherwise,
fall back to order.liveLocation from Prisma. This fallback supports old orders
and makes the rollout safe.

Recommended response shape:

    res.json({
        location: cachedLocation ? JSON.parse(cachedLocation) : order.liveLocation,
        status: order.status,
    });

When a delivery is completed or cancelled, delete the temporary key:

    await redis.del(`delivery:location:${order.id}`);

The map UI does not need a Redis-specific change. These existing client files keep
the same API contract:

    client/src/pages/OrderTracking.tsx
    client/src/components/OrderTracking/LiveMap.tsx
    client/src/components/delivery/DeliveryDashboard.tsx

Optional later improvement: replace polling with Redis Pub/Sub plus WebSockets or
Server-Sent Events. Do not start there; the current 10-second polling flow works
with a Redis-backed location endpoint.

Feature D: Rate limiting with Redis
-----------------------------------
Add a middleware file:

    server/middleware/rateLimit.ts

Use a key such as:

    rate:otp:<email>:<minute>

Increment it with Redis INCR and set EX: 60 on the first request. Reject the
request with HTTP 429 after a small limit, such as 3 OTP requests per 10 minutes.
Apply the middleware in server/routes/authRoutes.ts only to /send-otp first.
This protects the expensive email operation without changing the frontend.

Suggested implementation order
--------------------------------
1. Install redis and create server/config/redis.ts.
2. Connect Redis during server startup and verify the server still starts.
3. Move registration OTP storage from Map to Redis.
4. Add flash-deal caching and product cache invalidation.
5. Move live delivery location reads/writes to Redis.
6. Add rate limiting.
7. Consider Pub/Sub/WebSockets only if polling becomes a performance problem.

Testing checklist
-----------------
1. Start Redis, then start the server with npm run server.
2. Request an OTP, restart the server, and confirm the OTP still works.
3. Request flash deals twice and confirm the second request can use the cache.
4. Update a product as admin and confirm the old cached response is cleared.
5. Send delivery coordinates and call /api/orders/:id/location.
6. Confirm the location expires after its TTL.
7. Confirm a delivery partner cannot update another partner's order location.
8. Start the server without Redis and decide whether production should fail fast
   or whether Redis should be treated as an optional dependency. For OTP and live
   tracking, failing fast is usually safer than silently losing temporary data.
